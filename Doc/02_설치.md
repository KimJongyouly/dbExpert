# dbExpert Plugin 설치 가이드

## 0. 이 문서에 대해

이 문서는 [`00_개발요건사항.md`](./00_개발요건사항.md)/[`01_개발정의서.md`](./01_개발정의서.md)로
설계·구현된 `dbExpert` Plugin을 실제로 로컬에 설치하고 Claude Code에서
쓸 수 있는 상태로 만드는 절차를 단계별로 정리한다. 모든 명령은
이 저장소를 clone한 디렉터리(이하 `<plugin-root>`, `.claude-plugin/plugin.json`이
있는 곳)에서 실행하는 것을 기준으로 한다.

```bash
git clone https://github.com/<your-account>/dbExpert.git
cd dbExpert          # 이 디렉터리가 <plugin-root>
```

이 문서에 적힌 명령 중 `claude plugin validate`, `claude --plugin-dir`,
`uv sync` 등은 이 작업 중 실제로 실행해 동작을 확인한 것이며, 확인하지
못한 부분(예: 특정 회사 프록시 환경에서의 다운로드 속도)은 "확인 필요"로
명시한다 — 추측을 사실처럼 적지 않는다.

## 1. 사전 준비물

| 항목 | 필수 여부 | 비고 |
|---|---|---|
| Python 3.11 이상 | 필수 | `pyproject.toml`의 `requires-python` |
| [`uv`](https://docs.astral.sh/uv/) | 필수 | 의존성 설치/venv 관리 |
| Claude Code CLI | 필수 | Plugin을 실행할 호스트 |
| Docker | 선택 | `tests/integration/`(실제 DB로 검증하는 통합 테스트)에서만 필요. Plugin을 실제로 쓰는 데는 불필요 |
| JVM(Java Runtime) | 선택 | **Tibero**를 쓸 때만 필요(JPype가 JDBC Driver를 실행하기 위한 브릿지). 다른 7개 Engine에는 전혀 필요 없음 |

### 1.1 Python 버전 확인

```bash
python3 --version   # 3.11 이상이어야 한다
```

### 1.2 uv 설치 확인/설치

이미 설치되어 있는지 먼저 확인한다.

```bash
uv --version
```

없다면 다음 중 편한 방법으로 설치한다.

```bash
# macOS (Homebrew)
brew install uv

# pipx
pipx install uv

# 공식 설치 스크립트 (macOS/Linux)
curl -LsSf https://astral.sh/uv/install.sh | sh
```

설치 후 새 터미널을 열거나 쉘을 재시작하고 `uv --version`이 출력되는지
다시 확인한다.

### 1.3 (Tibero를 쓸 경우만) JVM 설치 확인 + JDBC 드라이버 준비

Tibero는 두 가지를 사용자가 직접 준비해야 한다.

1. **JVM(Java Runtime)** — 아래 명령으로 확인/설치한다.
2. **Tibero JDBC 드라이버(`tibero6-jdbc.jar`)** — TmaxData 배포물이라 이
   저장소에 포함하지 않는다. 대상 서버 버전에 맞는 jar를 구해
   `<plugin-root>/drivers/tibero/tibero6-jdbc.jar` 경로에 둔다
   (`drivers/tibero/README.md` 참고). 파일이 없으면 Tibero Connection만
   `DBConnectionError`로 실패하고 다른 Engine은 영향받지 않는다.

```bash
java -version
```

버전 정보가 출력되지 않으면 설치한다.

```bash
# macOS (Homebrew)
brew install openjdk

# Ubuntu/Debian
sudo apt-get install -y default-jre
```

JVM은 `JPype1` pip 패키지와는 별개의 운영체제 설치물이다 — `JPype1`만
설치해서는 부족하다(`drivers/tibero/README.md` 참고). Tibero를 안 쓴다면
이 단계는 완전히 건너뛰어도 된다.

## 3. Python 의존성 설치 (`uv sync`)

### 3.1 Extras(선택 설치) 개요

`pyproject.toml`은 기본 의존성(MCP Server, MySQL/PostgreSQL Driver 등)만
필수로 두고, 나머지 7개 Engine과 Ontology/RAG 스택은 전부 **선택
설치(extras)**로 분리해뒀다 — 안 쓰는 Engine의 무거운 Driver를 억지로
깔지 않기 위해서다.

| Extra | 내용 | 필요할 때 |
|---|---|---|
| `clickhouse` | clickhouse-connect | ClickHouse 연결 시 |
| `mongodb` | pymongo | MongoDB 연결 시 |
| `elasticsearch` | elasticsearch-py | 순정 Elasticsearch 연결 시 |
| `opensearch` | opensearch-py | OpenSearch(ElastiCache 등) 연결 시 |
| `redis` | redis-py | Redis/ElastiCache 연결 시 |
| `mssql` | pymssql | MSSQL 연결 시 |
| `tibero` | JPype1 | Tibero 연결 시 (+ 위 1.3의 JVM 설치 별도 필요) |
| `ontology` | lancedb, sentence-transformers | Ontology/RAG(스키마 검색, ERD) 기능을 쓸 때 — **아래 4장 참고, 최초 실행 시 대용량 모델 다운로드 발생** |
| `dev` | pytest, testcontainers | 테스트 실행 시에만(실사용에는 불필요) |
| `all` | 위 Engine 7개 + ontology 전부 | 어떤 Engine을 쓸지 아직 정하지 않았거나, 한 번에 전부 설치하고 싶을 때 |

### 3.2 설치 실행

가장 간단한 방법 — 전부 설치(이 문서에서 실제로 검증한 방식):

```bash
uv sync --extra all --extra dev
```

또는 실제로 쓸 Engine만 골라서:

```bash
uv sync --extra mysql --extra postgresql   # 예시 — 실제로는 mysql/postgresql은 기본 포함이라 생략 가능
uv sync --extra mongodb --extra clickhouse --extra ontology
```

### 3.3 실행하면 어떤 일이 일어나는가

- `.venv/` 디렉터리가 생성된다(Plugin 전용 가상환경).
- `uv.lock` 파일이 생성/갱신된다 — 정확한 버전까지 고정된 잠금 파일이라,
  다음에 다른 컴퓨터에서 `uv sync`를 실행해도 동일한 버전이 깔린다.
- 이 문서 작성 시점 기준 `--extra all --extra dev`는 **136개 패키지**를
  받는다(실제 실행 결과: `Resolved 136 packages`) — `torch`,
  `sentence-transformers`, `pandas`, `pyarrow` 등 용량이 큰 패키지가
  포함되어 있어 순수 설치 자체도 네트워크 상황에 따라 수 분 걸릴 수 있다.
  **이건 4장에서 설명하는 HuggingFace 모델 다운로드와는 다른 단계다** —
  `uv sync`는 Python 패키지(라이브러리 코드)만 받고, 실제 AI 모델
  가중치는 아직 받지 않는다.

### 3.4 설치 확인

```bash
uv run --no-sync python -c "import server.main; print('OK')"
```

`OK`가 출력되면 모든 모듈이 정상적으로 import되는 것이다(의존성 하나라도
빠지면 여기서 `ModuleNotFoundError`가 난다).

### 3.5 (참고) `mcp` 패키지 버전이 `<2.0.0`으로 고정되어 있는 이유

`pyproject.toml`을 열어보면 `mcp>=1.0.0,<2.0.0`으로 상한이 걸려 있다.
`mcp` 2.x는 이 Plugin이 쓰는 `FastMCP` API를 `MCPServer`로 이름을 바꿔서,
상한 없이 설치하면 `server/main.py`가 `ModuleNotFoundError:
mcp.server.fastmcp`로 아예 기동하지 못한다 — 실제로 재현되어 고정해둔
것이니 임의로 상한을 풀지 않는다.

## 4. HuggingFace Embedding 모델 다운로드 (Ontology/RAG 기능)

`ontology` extra(또는 `all`)를 설치했다면 이 장을 반드시 읽는다.

### 4.1 언제 다운로드되는가

**`uv sync` 시점이 아니라, Ontology 관련 Tool을 실제로 처음 호출하는
시점**에 다운로드된다 — `sentence-transformers`는 pip 패키지일 뿐이고,
그 패키지가 실제로 쓰는 언어 모델(가중치 파일)은 HuggingFace Hub에서
런타임에 받아온다. 처음 다운로드가 트리거되는 경우:

- `build_ontology_index` Tool을 처음 호출할 때
- `search_object_catalog` Tool을 호출했는데 해당 Connection의 Vector
  Index가 아직 비어있어서 자동으로 채우는 경우(Doc/00 §10.2 "쿼리 트리거
  기반 자동 갱신" — 2026-09 추가된 동작)
- Table 단위 자동 갱신(`server/catalog/auto_refresh.py`)이 처음 동작할 때

즉 **Ontology 기능을 아예 쓰지 않으면 이 모델은 영원히 다운로드되지
않는다.** MySQL Slow Query 조회 같은 기본 기능만 쓴다면 이 장은 무시해도
된다.

### 4.2 무엇을, 얼마나 받는가

- 모델: [`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2)
  (다국어 지원 — 한국어 포함 50개 이상 언어를 하나의 벡터 공간에 임베딩,
  출력 차원 384, Apache-2.0 라이선스)
- 이 모델을 고른 이유: 테이블/컬럼 comment가 한국어와 영어가 섞여 있는
  환경을 전제로 했고, CPU만으로도 수천 개 객체를 몇 분 안에 임베딩할 수
  있는 크기이며, 외부 API 호출 없이 완전히 로컬에서 동작하기 때문이다
  (`server/catalog/embeddings.py`).
- 실제 측정한 디스크 사용량(이 환경에서 캐시된 모델을 직접 확인한 값):
  **약 458MB**
- 저장 위치(기본값): `~/.cache/huggingface/hub/models--sentence-transformers--paraphrase-multilingual-MiniLM-L12-v2/`
  (Windows는 `%USERPROFILE%\.cache\huggingface\hub\...`)
- **딱 한 번만** 다운로드되고, 이후에는 로컬 캐시를 그대로 재사용한다
  (재다운로드 없음). 캐시를 지우면(`rm -rf ~/.cache/huggingface`) 다음
  실행 때 다시 받는다.

### 4.3 다운로드 시간이 얼마나 걸리는가

458MB 기준으로 계산한 **추정치**다(실제 소요 시간은 네트워크 환경에 따라
다르며, 아래 표는 순수 회선 속도 기준 계산값이지 이 환경에서 실측한 값은
아니다 — 사내망 프록시/방화벽이 있는 환경은 별도 확인이 필요하다):

| 회선 속도 | 예상 소요 시간 |
|---|---|
| 500Mbps (기가인터넷급) | 약 10초 |
| 100Mbps (일반 광랜) | 약 40초 ~ 1분 |
| 20Mbps | 약 3~4분 |
| 5Mbps (느린 회선/테더링) | 약 12~15분 |

체감상 "몇 초~몇 분" 사이인 경우가 대부분이지만, **회사 프록시나 방화벽이
`huggingface.co`를 막아두면 아예 실패**할 수 있다 — 이 경우 Tool 호출이
타임아웃되거나 연결 오류로 실패한다(증상: `search_object_catalog`/
`build_ontology_index` 최초 호출이 평소보다 훨씬 오래 걸리다가 실패).

### 4.4 첫 사용 지연을 없애고 싶다면 — 미리 받아두기(권장)

Plugin을 실제로 쓰기 전에 미리 모델을 받아두면, 실제 작업 중 첫 Tool
호출이 느려지는 걸 피할 수 있다. 저장소에 스크립트가 포함되어 있다.

```bash
uv run --no-sync python scripts/download_embedding_model.py
```

이 스크립트는 `server/catalog/embeddings.py`와 동일한 모델 이름을 사용해
캐시를 채우고, 로드된 모델의 출력 차원이 코드가 기대하는 값(384)과
일치하는지까지 확인한다. 조용한 시간(네트워크가 여유 있을 때)에 한 번
실행해두면 된다.

### 4.5 캐시 위치를 바꾸고 싶다면

HuggingFace 라이브러리 공통 환경변수인 `HF_HOME`으로 캐시 디렉터리를
바꿀 수 있다(디스크 용량이 부족한 홈 디렉터리를 피하고 싶을 때 등).

```bash
export HF_HOME=/path/to/large-disk/huggingface-cache
```

MCP Server는 Claude Code가 하위 프로세스로 띄우므로, 이 값도 `.env`에
같이 적어두는 것이 확실하다(§5.2와 같은 이유).

### 4.6 폐쇄망/프록시 환경 — 로컬 경로로 모델 지정

`huggingface.co`에 접근할 수 없는 환경이면, 인터넷이 되는 PC에서 §4.4로
모델을 받은 뒤 그 디렉터리를 통째로 옮기고 환경변수로 경로를 준다.

```bash
# 1) 인터넷이 되는 PC에서 받아서 디렉터리로 저장
uv run --no-sync python scripts/download_embedding_model.py --save-to ./models/multilingual-minilm

# 2) 옮긴 PC의 .env
DBEXPERT_EMBEDDING_MODEL=/absolute/path/to/models/multilingual-minilm
HF_HUB_OFFLINE=1
```

`DBEXPERT_EMBEDDING_MODEL`은 HuggingFace repo id 또는 로컬 디렉터리 경로를
받는다. 기본 모델이 아닌 **다른** 모델을 지정할 때는 출력 차원도
`DBEXPERT_EMBEDDING_DIM`으로 함께 알려줘야 하고, 이미 만들어진
`data/ontology_index/<connection>/lancedb/`는 지우고 다시 만들어야 한다
(벡터 차원이 스키마에 고정되어 있다).

## 5. Connection Profile 설정

### 5.1 `config/connections.yaml` 편집

예시 파일을 복사해서 실제 파일을 만든다. `config/connections.yaml`은
`.gitignore`에 등록되어 있어 커밋되지 않는다.

```bash
cp config/connections.example.yaml config/connections.yaml
```

이 파일을 열어:

1. 실제로 쓸 Connection만 남기고 나머지는 지우거나 주석 처리한다.
2. `host`/`port`/`database` 등 예시 값을 실제 값으로 바꾼다.
3. Bastion(SSH Tunnel)을 거쳐야 하면 `ssh.enabled: true`로 켜고
   `login_mode`(`pem` 또는 `password`)에 맞는 필드를 채운다
   (`config/connections.example.yaml`의 예시 참고).

### 5.2 계정/비밀번호는 `.env`로

`connections.yaml`에는 비밀번호를 절대 평문으로 적지 않는다 —
`user_env`/`password_env`에 "환경변수 이름"만 적어두면
`ConnectionManager`가 실행 시점에 `os.environ`에서 실제 값을 읽는다.

실제 값은 **Plugin 루트의 `.env` 파일**(`config/connections.yaml`과 같은
이유로 `.gitignore`에 이미 등록되어 있어 커밋되지 않는다)에 적는다.

```bash
# /path/to/dbExpert/.env
DBEXPERT_MYSQL_ADMIN_USER=실제계정
DBEXPERT_MYSQL_ADMIN_PASSWORD=실제비밀번호
# ... 나머지 Connection도 동일하게

chmod 600 .env   # 본인만 읽을 수 있게
```

⚠️ **쉘 프로파일(`~/.zshrc` 등)에 `source`해두는 방식은 쓰지 않는다** —
실제로 겪은 문제: Claude Code는 MCP Server를 하위 프로세스로 띄울 때
사용자의 로그인 쉘 프로파일을 거치지 않는다. 그래서 거기서만 `export`해둔
값은 MCP Server 프로세스에 전혀 전달되지 않고, `server/main.py`가
`.claude-plugin`을 통해 기동되는 순간 자격증명을 하나도 못 찾아 그대로
죽어버린다(Claude Code 쪽에는 그냥 "MCP 서버 연결 끊김"으로만 보여서
원인을 알기 어렵다 — 실제로 이 증상으로 재현/진단했다).

대신 `server/main.py`가 시작할 때 `python-dotenv`로 이 `.env` 파일을
**직접** 읽어 들이므로(쉘을 거치지 않음), 어떤 방식으로 MCP Server가
기동되든 항상 같은 값을 본다. 별도로 `source`하거나 쉘 프로파일을 고칠
필요가 없다 — 파일만 채워두면 끝이다.

값을 제대로 읽는지 확인하려면:

```bash
uv run --no-sync python -c "
from dotenv import load_dotenv
load_dotenv('.env')
import os
print('OK' if os.environ.get('DBEXPERT_MYSQL_ADMIN_USER') else 'MISSING')
"
```

### 5.3 별도 Read Only 계정을 발급받기 어려운 경우 참고

관리 권한 계정을 그대로 써야 하는 환경이라면,
MySQL/PostgreSQL/ClickHouse/Tibero는 코드가 연결 직후 세션 자체를 서버
레벨에서 Read Only로 강제하므로 추가 조치가 필요 없다. **MSSQL만은**
이 방식이 불가능해 텍스트 가드가 유일한 방어선이므로, MSSQL을 쓴다면
별도 Read Only 계정 발급을 강력히 권장한다(`server/database/mssql.py`
참고, Doc/00 §29).

### 5.4 설정이 제대로 읽히는지 확인

```bash
uv run --no-sync python -c "
from server.connection.manager import ConnectionManager
m = ConnectionManager('config/connections.yaml')
m.load()
print(m.list_connections())
"
```

정상적으로 자격증명을 채운 Connection들만 `name`/`db_type` 목록으로
나온다. 환경변수를 안 채운(또는 틀린) Connection이 있어도 **그 Connection만
조용히 건너뛰고 나머지는 정상 동작한다** — `list_load_errors()`로 어떤
Connection이 왜 빠졌는지 확인할 수 있다.

```bash
uv run --no-sync python -c "
from server.connection.manager import ConnectionManager
m = ConnectionManager('config/connections.yaml')
m.load()
print('로드됨:', [c['name'] for c in m.list_connections()])
print('실패:', m.list_load_errors())
"
```

Connection이 하나라도 실패해도 MCP Server 프로세스 자체는 죽지 않는다
(2026-09 이전에는 등록된 Connection 중 단 하나의 자격증명만 빠져도
`ConnectionManager.load()`가 예외를 던져 서버 전체가 기동 직후 죽는
버그가 있었다 — 지금은 고쳐졌다).

## 6. Claude Code에 Plugin 로드하기

### 6.1 Plugin 자체 검증 (실제 검증됨)

```bash
claude plugin validate .
```

이 명령을 실제로 실행해 `✔ Validation passed`를 확인했다 —
`.claude-plugin/plugin.json`이 Claude Code 공식 스펙을 만족한다는 뜻이다.

### 6.2 로컬 개발/개인 사용 — `--plugin-dir` (권장, 실제 검증됨)

퍼블리시하지 않고 본인 PC에서만 쓰는 상황이라면, Claude Code 실행 시
`--plugin-dir` 플래그로 이 디렉터리를 직접 지정하는 게 가장 간단하다
(이 방식이 실제 설치된 `claude` CLI의 `--help`에 정식 옵션으로 존재함을
확인했다).

```bash
claude --plugin-dir <plugin-root>
```

이렇게 실행한 세션에서는 `db_ping`, `slow_query_list` 등 23개 Tool과
7개 Skill(`db-error`, `slow-query`, `index-tuning`, `query-tuning`,
`data-pipeline`, `erd-builder`, `query-builder`)이 전부 로드된다.

매번 이 플래그를 치기 번거로우면 쉘 alias를 만들어두면 편하다.

```bash
# ~/.zshrc 등에 추가
alias dbExpert='claude --plugin-dir <plugin-root>'
```

### 6.3 영구 등록 — Marketplace 방식

처음에는 `claude plugin marketplace add`로 이 폴더를 직접 등록하려다
**단일 Plugin 폴더만으로는 안 되고** `.claude-plugin/marketplace.json`
(Plugin 목록 매니페스트)이 있어야 한다는 걸 확인했다(`Marketplace file not
found` 오류). 지금은 그 파일이 저장소에 포함되어 있어, 아래처럼 등록하면
`--plugin-dir` 플래그 없이 모든 세션에서 자동으로 로드된다. Claude Code
안에서 슬래시 명령으로 입력한다.

```
/plugin marketplace add <your-account>/dbExpert     # GitHub에서 직접
/plugin marketplace add <plugin-root>               # 또는 로컬 clone 경로
/plugin install dbExpert@dbExpert
```

마켓플레이스 이름과 플러그인 이름이 둘 다 `dbExpert`라 `dbExpert@dbExpert`
형태가 된다. 인터랙티브 UI(`/plugin`)로 같은 작업을 하는 절차는
`README.md`에 정리해두었다.

## 8. 자주 겪는 문제

| 증상 | 원인/해결 |
|---|---|
| `ModuleNotFoundError: mcp.server.fastmcp` | `uv sync`를 이 Plugin의 `pyproject.toml`이 아닌 다른 환경에서 했거나, `mcp` 상한을 임의로 풀었을 가능성 — §3.5 참고 |
| `환경변수 XXX 가 설정되어 있지 않습니다` (`AuthenticationError`) | §5.2의 `.env`에 그 이름으로 값을 안 채웠거나 오타 — §5.4의 확인 명령으로 어떤 Connection이 실패했는지 본다 |
| Claude Code에서 dbExpert MCP 서버가 "연결 끊김(CONNECTION_CLOSED)"으로 뜸 | 실제로 겪은 증상 — 원인은 대부분 위 `AuthenticationError`다(§5.2 참고). MCP Server가 하위 프로세스로 뜰 때 쉘 프로파일을 안 거치므로, `.env`를 Plugin 루트에 두지 않고 `~/.zshrc`에서 `export`만 해뒀다면 이 증상이 난다 — 2026-09 이후 버전은 Connection 하나의 자격증명 실패가 서버 전체를 죽이지 않도록 고쳐졌지만, `.env` 자체가 없거나 위치가 틀리면 여전히 아무 Connection도 못 쓴다 |
| `config/connections.yaml 가 존재하지 않습니다` | `config/connections.example.yaml`을 `connections.yaml`로 복사부터 한다(이미 되어 있다면 경로/실행 위치 확인) |
| `search_object_catalog`/`build_ontology_index` 최초 호출이 아주 오래 걸리거나 멈춤 | HuggingFace 모델 다운로드 중이거나(§4), 네트워크가 `huggingface.co`를 막고 있을 가능성 — §4.4로 미리 워밍업 |
| Tibero 연결 시 `Tibero JDBC Driver를 찾을 수 없습니다` | jar는 저장소에 포함되지 않는다 — §1.3대로 `drivers/tibero/tibero6-jdbc.jar`를 직접 준비한다 |
| Tibero 연결 시 JVM 관련 에러 | §1.3의 JVM 설치 여부 확인. `java -version`이 동작해야 한다 |
| Tibero 연결은 되는데 쿼리 결과가 이상함 | `drivers/tibero/README.md` 참고 — Tibero 5.0 서버 + 6.0.166454 드라이버 조합만 검증됨. 다른 조합은 직접 확인 필요 |
| `search_object_catalog` 결과가 이상하거나 LanceDB 차원 오류 | `DBEXPERT_EMBEDDING_MODEL`을 바꿨다면 §4.6대로 `DBEXPERT_EMBEDDING_DIM`을 맞추고 기존 `data/ontology_index/<connection>/`를 지운 뒤 재구축 |
| MSSQL 연결 실패 | `pyodbc`가 아니라 `pymssql`(FreeTDS 기반)을 쓰므로 OS ODBC Driver는 필요 없다 — `uv sync --extra mssql` 여부, 방화벽/포트(기본 1433) 확인 |
