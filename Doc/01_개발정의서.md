# dbExpert Plugin 개발정의서

## 0. 문서 개요

본 문서는 [00_개발요건사항.md](./00_개발요건사항.md)에 정의된 요건을 실제 개발에 착수할 수 있는 수준으로 구체화한 **개발정의서**이다.

문서 간 역할 구분:

| 문서 | 성격 | 다루는 내용 |
|---|---|---|
| 00_개발요건사항.md | 요건정의서 (What / Why) | Plugin의 목적, Skill 분류, 기능별 목적과 사용자 시나리오, 정책(보안/Read Only 등) |
| 01_개발정의서.md (본 문서) | 개발정의서 (How) | Tool Interface 명세, 데이터 모델, 모듈 설계, 처리 흐름, 개발 착수 기준 |

본 문서는 00 문서의 각 기능을 재설명하지 않고, 00에서 서술형으로 흩어져 있던 내용(Tool Input/Output, Phase, 디렉터리 구조 등)을 **구현 가능한 명세**로 정리하는 데 집중한다. 00 문서와 표현이 다를 경우, 본 문서가 구현 기준이며 00 문서는 이후 본 문서에 맞춰 갱신한다.

표기 규칙:

- Tool Input/Output은 TypeScript 유사 표기로 정의한다. `?`는 optional, `[]`는 배열을 의미한다.
- Read Only 여부는 [00 §29 보안 요구사항](./00_개발요건사항.md)의 원칙을 따르며, 모든 Tool은 기본적으로 Read Only이다. 예외는 각 Tool에 명시한다.

## 1. 시스템 구성 요약

```text
[Claude] ── Skill 선택 ──▶ [MCP Tool 호출] ──▶ [Adapter Registry] ──▶ [Database Adapter] ──▶ [Engine]
                              │                        │
                              │                        └──▶ db_type으로 Adapter 클래스 조회
                              ├──▶ [Ontology Index Store (Vector)]
                              └──▶ [Q&A Log Store / Query Pattern Store]
```

계층 구조:

| 계층 | 구성 요소 | 비고 |
|---|---|---|
| Skill 계층 | db-error, slow-query, index-tuning, query-tuning, data-pipeline | 사용자 의도에 따라 Claude가 선택. [5. Skill 라우팅 정의](#5-skill-라우팅-정의) 참고 |
| MCP Tool 계층 | 3장에서 정의하는 전체 Tool | Skill 간 공유 가능. Engine에 무관하게 Tool 이름은 고정 |
| Adapter Registry 계층 | `database/registry.py` | `db_type` → Adapter 클래스 조회. 신규 Engine 추가의 유일한 등록 지점 |
| Adapter 계층 | Database Adapter(MySQL/PostgreSQL/Tibero/MSSQL/ClickHouse/MongoDB/Elasticsearch·OpenSearch/Redis) | Engine 차이를 흡수하는 추상화 계층. Capability 단위로 구현 |
| Storage 계층 | Ontology Index(Vector Store), Q&A Log/Query Pattern Store, Connection Profile | Plugin 자체 상태 저장소 (DB 외부, `data/` 하위) |
| 외부 계층 | RDB(MySQL/PostgreSQL/Tibero), DW(ClickHouse), Document(MongoDB), Search(Elasticsearch/OpenSearch), Key-Value(Redis/ElastiCache) — Direct 또는 Bastion 경유 | Read Only 접근만 허용. Engine Family 분류는 [00 §7](./00_개발요건사항.md) 참고 |

본 문서에서 "DBMS"라는 표현은 관행상 남아있는 경우에도 RDB/DW/Document/Search/Key-Value를 포괄하는 **Engine**을 의미하는 것으로 통일한다.

## 2. 공통 인터페이스 정의

### 2.1 Connection Manager 인터페이스

`server/connection/manager.py`

```text
ConnectionManager
  - get_connection(name: string) -> DBHandle
      : Connection Profile을 조회하여 Direct 또는 SSH Tunnel(Bastion) 경유로
        DB Handle을 반환한다. Tunnel이 필요한 경우 내부적으로 ssh_tunnel.py를 사용한다.
  - release(handle: DBHandle) -> void
      : 연결/Tunnel을 정리한다. (Connection Pool을 쓰지 않는 MVP 단계에서는
        요청 단위로 connect/release한다.)
  - list_connections() -> ConnectionProfile[]
      : config/connections.yaml에 정의된 전체 Connection 목록을 반환한다.
```

Timeout은 [00 §33 Timeout](./00_개발요건사항.md)의 기본값(Connection 5s / Query 30s / SSH 10s)을 Connection Manager와 Database Adapter 양쪽에서 강제한다.

### 2.2 Database Adapter 인터페이스 (Capability 기반)

`server/database/base.py`

[00 §7 지원 Data Store](./00_개발요건사항.md)에서 정의한 대로, RDB 외에 DW/Document/Search/Key-Value Engine을 함께 다루므로 단일 거대 인터페이스 대신 **Capability 단위의 Mixin 인터페이스**로 정의한다. `BaseAdapter`는 모든 Engine이 구현하는 최소 공통 인터페이스이며, 나머지는 Engine이 실제로 지원하는 Capability만 선택적으로 구현한다.

```text
BaseAdapter (모든 Engine 필수 구현)
  - ping() -> {version: string, uptime_sec?: number}
  - capabilities: Set[Capability]     # 클래스 속성. 이 Adapter가 구현한 Capability 목록

Capability.SQL          → SqlCapable
  - execute_readonly(sql: string, params?: any[]) -> Row[]
      : SELECT/SHOW 등 허용된 구문만 실행. DDL/DML 감지 시 DDL_BLOCKED 에러.
  - explain(sql: string) -> ExplainPlan

Capability.SLOW_OP      → SlowOperationCapable
  - get_slow_operations(min_duration_sec: number, limit: number) -> SlowOperation[]
      : RDB/DW는 Slow Query, MongoDB는 Profiler 결과, ES/OpenSearch는 Slow Log,
        Redis는 SLOWLOG 결과를 동일한 SlowOperation 형태로 정규화하여 반환한다.

Capability.ACTIVITY     → ActivityCapable
  - get_locks() -> Lock[]
  - get_sessions() -> Session[]
      : Redis/ES는 Lock 개념이 없으므로 Blocked Client / 실행 중 Task로 대체 매핑.

Capability.ERROR_LOG    → ErrorLogCapable
  - get_errors(since?: datetime) -> DBError[]

Capability.SCHEMA       → SchemaCapable
  - get_schema(scope: SchemaScope) -> SchemaObject[]
      : Namespace/Container/Field 목록 + comment(있는 경우). Ontology 수집과
        DataEngineer의 get_schema Tool이 공통으로 사용한다.
      : Comment 미지원 Engine(MongoDB/ES/Redis)은 comment 없이 이름/타입만 반환하거나
        Sampling 기반으로 Field를 추론한다([00 §10.1](./00_개발요건사항.md) 매핑표 참고).

Capability.STATS        → StatisticsCapable
  - get_table_statistics(namespace: string, container: string) -> ContainerStatistics
  - get_index_statistics(namespace: string, container: string) -> IndexStatistics[]
      : Redis는 Index 개념이 없으므로 Key 패턴별 개수/메모리 사용량으로 대체.

Capability.RELATIONSHIP → RelationshipCapable
  - get_relationships(containers: string[]) -> Relationship[]
      : FK 제약을 조회. 선언된 FK가 없거나 Capability 자체가 없으면 빈 배열을 반환하고,
        컬럼명 패턴 기반 추정은 Adapter가 아닌 catalog/erd_builder.py에서 수행한다.

Capability.SAMPLE       → SampleCapable
  - sample_rows(namespace: string, container: string, limit: number, mask?: string[]) -> Row[]
      : DataEngineer의 Raw Data 샘플 조회 전용. limit은 서버 설정 상한을 넘을 수 없다.
      : Redis는 SCAN 기반으로 Key 패턴당 대표 값을 Sample로 반환한다.
```

MCP Tool 실행기는 호출 전 `adapter.capabilities`에 필요한 Capability가 있는지 확인하고, 없으면 [8. 에러 코드](#8-에러-코드-정의)의 `CAPABILITY_NOT_SUPPORTED`를 반환한다(예외가 아니라 정상 응답 형태의 "미지원 안내"로 처리하여 Claude가 자연스럽게 대체 설명을 할 수 있도록 한다).

SQL 기반 Engine(MySQL/PostgreSQL/Tibero/ClickHouse)은 `server/sql/<engine>/*.sql`([00 §30](./00_개발요건사항.md))의 쿼리를 사용하여 구현하며, 쿼리 문자열은 Adapter 코드에 하드코딩하지 않고 `.sql` 파일에서 로드한다. Query DSL/API 기반 Engine(MongoDB/Elasticsearch·OpenSearch/Redis)은 `server/query/<engine>/`의 템플릿(Aggregation Pipeline, Query DSL, 명령 템플릿)을 동일한 방식으로 로드한다([00 §30 SQL Injection 방지](./00_개발요건사항.md) 원칙을 Query DSL/명령 조합에도 동일 적용).

### 2.3 Engine별 구현 매핑

| Capability 메서드 | MySQL | PostgreSQL | Tibero | MSSQL | ClickHouse | MongoDB | Elasticsearch/OpenSearch | Redis/ElastiCache |
|---|---|---|---|---|---|---|---|---|
| explain | `EXPLAIN FORMAT=JSON` | `EXPLAIN (FORMAT JSON, ANALYZE FALSE)` | `EXPLAIN PLAN FOR` | `SET SHOWPLAN_XML ON` | `EXPLAIN` | `explain()` (aggregate/find) | `_explain` API | 미지원 |
| get_slow_operations | `performance_schema.events_statements_summary_by_digest` | `pg_stat_statements` | Tibero Performance View (확정 필요, [11.](#11-미결정-사항)) | `sys.dm_exec_query_stats` | `system.query_log` | `system.profile` (Profiler) | Slow Log 설정 조회 | `SLOWLOG GET` |
| get_locks/get_sessions | `performance_schema` / `information_schema.PROCESSLIST` | `pg_locks` / `pg_stat_activity` | `V$LOCK` / `V$SESSION` 계열 | `sys.dm_tran_locks` / `sys.dm_exec_sessions` | `system.processes` | `currentOp()` | Task API (제한적) | `CLIENT LIST` (Blocked 여부) |
| get_table_statistics | `information_schema.TABLES` | `pg_stat_user_tables` / `pg_class` | `ALL_TABLES` (Oracle 호환) | `sys.dm_db_partition_stats` / `sys.tables` | `system.parts` | `collStats` | `_stats` API | `DBSIZE` + Key 패턴별 `MEMORY USAGE` 샘플링 |
| get_index_statistics | `information_schema.STATISTICS` | `pg_stat_user_indexes` | `ALL_INDEXES` | `sys.dm_db_index_usage_stats` / `sys.indexes` | `system.parts` (Sort Key 기준) | `getIndexes()` / `$indexStats` | 명시적 Index 없음(Mapping/Shard 정보로 대체) | 미지원 |
| get_schema (comment) | `information_schema.COLUMNS` (`COLUMN_COMMENT`) | `pg_catalog.pg_description` | `ALL_COL_COMMENTS` | `sys.extended_properties` (`MS_Description`) | `system.columns` (`comment`) | 없음 (Sampling 기반 추론) | 없음 (`_meta` 있으면 사용) | 없음 (Key 패턴 문서로 대체) |
| get_relationships | `information_schema.KEY_COLUMN_USAGE` | `information_schema.table_constraints` + `key_column_usage` | `ALL_CONSTRAINTS` + `ALL_CONS_COLUMNS` | `sys.foreign_keys` + `sys.foreign_key_columns` | 없음 (항상 inferred) | 없음 (항상 inferred) | 미지원 | 미지원 |

### 2.4 Adapter Registry

`server/database/registry.py`

```text
AdapterRegistry
  - register(db_type: string, adapter_class: Type[BaseAdapter]) -> void
  - resolve(db_type: string) -> Type[BaseAdapter]
  - list_registered() -> { db_type: string, engine_family: string, capabilities: Capability[] }[]
```

MCP Server 기동 시 `mysql.py`~`redis.py`가 각자 자신을 `AdapterRegistry`에 등록한다(모듈 import 시점의 self-registration). Connection Manager는 Connection Profile의 `db_type`으로 `resolve()`를 호출해 Adapter 인스턴스를 생성하므로, [00 §7.3 확장 구조](./00_개발요건사항.md)에 따라 신규 Engine 추가 시 이 파일 외에는 수정할 필요가 없다.

## 3. MCP Tool 명세

아래 모든 Tool은 별도 명시가 없는 한 Read Only이며, `connection: string`을 공통 필수 입력으로 갖는다(표에서는 생략).

### 3.1 Common

#### `db_ping`
- Input: `{}`
- Output: `{ db_type: string, version: string, connected: boolean }`
- 비고: Phase 1 최초 연결 확인용.

#### `query_explain`
- Input: `{ sql: string, analyze?: boolean }`
- Output: `{ plan: object, scan_type: string, estimated_cost: number, estimated_rows: number, warnings: string[] }`
- 비고: `analyze: true`는 실제 실행을 유발하므로 기본 비활성화, 별도 승인 플래그 필요([00 §29](./00_개발요건사항.md)).

### 3.2 Maintenance

#### `db_error_analyze`
- Input: `{ error?: string, since?: datetime }`
- Output: `{ error_code: string, error_message: string, occurred_at: datetime, related_sessions: Session[], related_locks: Lock[], running_sql: string[], recent_slow_queries: SlowQuery[] }`
- 비고: `error`가 없으면 `since` 이후 DB 자체 Error Log에서 최근 오류를 조회(향후 `get_db_errors`로 분리 가능, [11. 미결정 사항](#11-미결정-사항) 참고).

#### `slow_query_list`
- Input: `{ min_duration: number, limit?: number(default 20, max 100) }`
- Output: `SlowQuery[]` — `{ query_id, sql_text, execution_count, avg_duration_ms, max_duration_ms, rows_examined, rows_sent, database, user, host, index_used?, last_seen }`

#### `get_locks` (Phase 8)
- Input: `{}`
- Output: `Lock[]` — `{ holding_session_id, waiting_session_id, table, lock_type, wait_time_ms }`

#### `get_sessions` (Phase 8)
- Input: `{ status?: "running" | "idle" | "all" }`
- Output: `Session[]` — `{ session_id, user, host, db, current_sql?, state, duration_ms }`

### 3.3 Tuner

#### `get_table_statistics`
- Input: `{ table: string, schema?: string }`
- Output: `{ row_count_estimate: number, size_bytes: number, last_analyzed_at?: datetime }`

#### `get_index_statistics`
- Input: `{ table: string, schema?: string }`
- Output: `IndexStat[]` — `{ index_name, columns: string[], cardinality: number, usage_count?: number, is_unique: boolean }`

#### `index_recommend`
- Input: `{ sql?: string, target_table: string }`
- Output: `{ existing_indexes: IndexStat[], missing_index_candidates: { columns: string[], reason: string }[], unused_index_candidates: string[], ddl_suggestion: string, trade_off: string }`
- 비고: 00 문서 내 `recommend_index()` 표기는 본 Tool의 동의어이며, **`index_recommend`를 표준 명칭**으로 확정한다([3.7](#37-tool-명명-정합성-정리) 참고).

#### `query_rewrite_suggest`
- Input: `{ sql: string }`
- Output: `{ issues: { pattern: string, description: string }[], suggested_sql: string, expected_effect: string }`
- 비고: 00 문서 내 `suggest_query_rewrite()` 표기는 본 Tool의 동의어이며, **`query_rewrite_suggest`를 표준 명칭**으로 확정한다.

### 3.4 DataEngineer

#### `list_raw_sources`
- Input: `{ scope: string }` (예: `"schema:raw_landing"`)
- Output: `{ type: "table" | "file", name: string, row_count?: number, size_bytes?: number }[]`

#### `get_schema`
- Input: `{ scope: string }`
- Output: `SchemaObject[]` — `{ schema, table, table_comment?, columns: { name, type, nullable, comment?, is_pk, is_fk }[] }`
- 비고: Ontology 수집(`build_ontology_index`)과 동일한 내부 함수(`database/base.py#get_schema`)를 사용한다.

#### `profile_data`
- Input: `{ table: string, schema?: string, sample_limit?: number(default 100, max 1000) }`
- Output: `{ null_ratio: { column: string, ratio: number }[], cardinality: { column: string, distinct_count: number }[], sample_rows: Row[] (마스킹 적용) }`

#### `generate_pipeline_plan`
- Input: `{ source: { type: "table"|"file", name: string }, target: { type: "table", name: string } }`
- Output: `{ column_mapping: { source_column: string, target_column?: string, transform?: string }[], unmapped_columns: string[], load_mode: "full" | "incremental", incremental_column?: string, schedule_suggestion: string, error_handling: string, code_draft?: string }`

#### `validate_pipeline`
- Input: `{ plan: object (generate_pipeline_plan 출력), sample_limit?: number(default 100) }`
- Output: `{ constraint_violations: { column: string, constraint: string, sample_value: any }[], cast_failures: { column: string, count: number }[], predicted_target_row_count: number }`

### 3.5 Ontology / ERD

#### `build_ontology_index`
- Input: `{ mode?: "full" | "incremental"(default) }`
- Output: `{ indexed_objects: number, updated: number, removed: number, duration_ms: number }`
- 비고: 유일하게 쓰기 작업(Vector Store에 대한 upsert)이 발생하는 Tool이지만, 대상 DB는 Read Only이며 Plugin 자체 저장소만 갱신한다.

#### `search_object_catalog`
- Input: `{ query: string, top_k?: number(default 5) }`
- Output: `{ matches: { schema: string, table: string, table_comment?: string, score: number, columns: { name: string, comment?: string }[] }[], index_was_empty_and_rebuilt: boolean }`
- 비고: 이 Connection의 Vector Index가 한 번도 채워지지 않았으면(최초 사용,
  Daily 배치 이전) 빈 결과만 내는 대신 그 자리에서 `build_ontology_index`를
  1회 실행해 채운 뒤 검색한다(`index_was_empty_and_rebuilt: true`로 표시).
  이미 문서가 있으면(단순히 이번 query와 매칭되는 게 없을 뿐이면) 재빌드하지
  않는다 — `server/catalog/object_search.py`, `rag_index.py::is_empty()`.

#### `get_table_relationships`
- Input: `{ scope: { tables: string[] } | { related_to: string } | { schema: string, limit?: number(default 20) } }`
- Output: `{ tables: { schema: string, table: string, comment?: string, columns: { name, type, is_pk, comment? }[] }[], relationships: { from_table: string, from_column: string, to_table: string, to_column: string, cardinality: "1:1"|"1:N", confidence: "declared"|"inferred" }[] }`
- 비고: 이 Tool의 출력을 Claude가 Mermaid `erDiagram` 문법으로 변환한다(Python은 변환하지 않음 — [00 §10.4](./00_개발요건사항.md) 원칙).

### 3.6 Learning (Q&A Logging / Pattern)

#### `log_qa`
- Input: `{ skill: string, question: string, tools_used: string[], objects_referenced: string[], sql_used?: string[](마스킹됨), answer_summary: string, duration_ms: number }`
- Output: `{ logged: boolean, log_id: string, queued: boolean }`
- 비고: 호출 주체는 여전히 Claude(Skill 실행 종료 시 명시적 호출)이지만, **실제 디스크 쓰기 시점**은 `server/learning/background_writer.py`(`QALogWriter`)가 미룬다 — Tool 호출은 메모리 Queue에 넣기만 하고 즉시 반환하며(`queued: true`), CPU 사용률이 낮고(기본 50% 이하) 마지막 Tool 호출로부터 일정 시간(기본 10초) 지나 "컴퓨터가 한가하고 Claude 작업이 없다"고 판단될 때만 실제로 append한다. 프로세스 종료 시(atexit)는 조건과 무관하게 즉시 flush해 유실을 막는다. "MCP Server가 가로채 자동 기록"하는 방식([11. 미결정 사항](#11-미결정-사항))은 여전히 미결정.

#### `summarize_query_patterns`
- Input: `{ since?: datetime, until?: datetime }` (미지정 시 마지막 배치 이후 전체)
- Output: `{ patterns_upserted: number, connections_processed: string[] }`
- 비고: Daily Scheduled Job에서 호출되는 것을 기본으로 하며, 수동 호출도 허용한다.

#### `get_query_patterns`
- Input: `{ limit?: number(default 20), related_object?: string }`
- Output: `QueryPattern[]` — 4.5 참고.

### 3.7 Tool 명명 정합성 정리

00 문서 작성 과정에서 아키텍처 다이어그램(§3)과 상세 기능 설명(§16, §17) 간 Tool 이름 표기가 달랐던 항목을 다음과 같이 표준화한다.

| 00 문서 내 등장 표기 | 표준 명칭 (본 문서 기준) |
|---|---|
| `recommend_index()` | `index_recommend` |
| `suggest_query_rewrite()` | `query_rewrite_suggest` |
| `get_slow_queries()` (§24 향후 Tool) | `slow_query_list`의 확장판으로 통합, 별도 Tool 신설 안 함 |
| `get_db_errors()` (§24 향후 Tool) | `db_error_analyze`의 `error` 파라미터 생략 호출로 통합, 별도 Tool 신설 안 함 |

### 3.8 Tool ↔ Capability 매핑

각 Tool은 실행 시 대상 Adapter가 아래 Capability를 지원하는지 확인한다. 지원하지 않으면 `CAPABILITY_NOT_SUPPORTED`를 반환하고, Claude는 이를 "이 Data Store에는 해당 기능이 적용되지 않습니다"와 같이 사용자에게 안내한다.

| Tool | 요구 Capability | 미지원 가능 Engine |
|---|---|---|
| `query_explain` | SQL | MongoDB, Elasticsearch/OpenSearch, Redis (각각 explain 유사 API로 대체 검토, [11.](#11-미결정-사항)) |
| `db_error_analyze` | ERROR_LOG, ACTIVITY | 없음(모든 Engine 어떤 형태로든 지원) |
| `slow_query_list` | SLOW_OP | 없음(모든 Engine이 Slow Operation 개념을 가짐) |
| `get_locks` / `get_sessions` | ACTIVITY | Elasticsearch/OpenSearch, Redis는 제한적 결과(빈 배열 또는 근사치) |
| `get_table_statistics` / `get_index_statistics` | STATS | Redis의 Index Statistics는 미지원 |
| `index_recommend` | STATS, SQL 또는 SCHEMA | Elasticsearch/OpenSearch/Redis는 Index DDL 대신 Mapping/Key 설계 조언으로 대체 응답 |
| `query_rewrite_suggest` | SQL | MongoDB/Elasticsearch/Redis는 미지원(Query DSL 최적화 제안은 향후 별도 Tool로 검토) |
| `list_raw_sources` / `get_schema` / `profile_data` | SCHEMA, SAMPLE | Redis는 Key 패턴 기반으로 대체 |
| `generate_pipeline_plan` / `validate_pipeline` | SCHEMA, SAMPLE | 모든 Engine이 Source/Target으로 참여 가능(Capability가 없는 필드는 매핑 불가로 표시) |
| `build_ontology_index` / `search_object_catalog` | SCHEMA (comment 없어도 이름 기반으로 동작) | 없음 |
| `get_table_relationships` | RELATIONSHIP | Elasticsearch/OpenSearch, Redis는 빈 relationships 반환 |
| `log_qa` / `summarize_query_patterns` / `get_query_patterns` | 없음(Engine 무관, Plugin 자체 저장소 기능) | 없음 |
| `find_query_pattern` | 없음(Engine 무관, Plugin 자체 저장소 기능) | 없음 |
| `execute_readonly_query` | SQL | MongoDB, Elasticsearch/OpenSearch, Redis (Query DSL 기반 Engine은 대신 `sample_rows` 등 기존 Tool로 대체) |

### 3.9 Query Builder (자연어 조회, `query-builder` Skill)

#### `find_query_pattern`
- Input: `{ question: string, top_k?: number(default 5), min_score?: number(default 0.5) }`
- Output: `{ matches: (QueryPattern & { score: number })[] }` — QueryPattern은 [4.5](#45-query-pattern-schema) 참고
- 비고: `get_query_patterns`의 `related_object` 정확 일치 검색과 달리, `question`을
  Ontology 검색과 동일한 Embedding(`server/catalog/embeddings.py`)으로 벡터화해
  `representative_question`과 의미 유사도로 비교한다. `data/qa_logs/<connection>/
  patterns.json`이 비어있으면(아직 학습 전) 빈 배열을 반환한다 — 정상 동작이며,
  이 경우 Claude는 `search_object_catalog`부터 시작한다.

#### `execute_readonly_query`
- Input: `{ sql: string, limit?: number(default 100, max 1000), mask?: string[] }`
- Output: `{ rows: Row[], row_count: number, truncated: boolean }`
- 비고: 기존 Tool은 전부 특정 목적(느린 쿼리, 통계, 샘플 등)에 고정돼 있어
  자유로운 자연어 조회에 쓸 수 없었다 — SQL 자체는 Claude가 `search_object_catalog`/
  `get_schema`로 확인한 실제 테이블·컬럼명으로 구성하고, 이 Tool은 그 SQL을
  안전하게 실행만 한다. Read Only 방어는 `execute_readonly()`의 기존 3중 방어
  (텍스트 가드 + 서버 세션 레벨 강제 + Query Timeout, [00 §29](./00_개발요건사항.md))를
  그대로 재사용하며 별도 방어를 추가하지 않았다. 결과 행은 DB에서 가져온 뒤
  Python 쪽에서 `limit`으로 자르므로(`sample_rows`와 동일 방식), SQL 자체에
  LIMIT을 포함하는 것을 권장한다.

## 4. 내부 데이터 모델 정의

### 4.1 Connection Profile Schema

`config/connections.yaml`

```text
ConnectionProfile
  - name: string (unique key)
  - db_type: "mysql" | "postgresql" | "tibero" | "mssql" | "clickhouse"
           | "mongodb" | "elasticsearch" | "opensearch" | "redis"
      # AdapterRegistry에 등록된 값이면 자유롭게 추가 가능 (00 §7.3)
  - engine_family: "rdb" | "dw" | "document" | "search" | "keyvalue"
      # db_type으로부터 자동 유추 가능하지만, 검증/라우팅 편의를 위해 명시 저장
  - connection: object
      # Engine에 따라 형태가 다르다:
      #   RDB/DW        : { host, port, database }
      #   MongoDB       : { uri_host, port, database }
      #                   또는 { uri }  (완전한 연결 문자열 — mongodb+srv://,
      #                   Replica Set(?replicaSet=rs0) 등. uri가 있으면 우선)
      #   Elasticsearch : { host, port }  (database 없음, index 단위로 접근)
      #   Redis         : { host, port, db_number }
      #                   또는 { cluster_mode: true, nodes: [{host, port}, ...] }
      #                   (ElastiCache Cluster Mode Enabled 등, §11 참고)
  - ssh?: { enabled: boolean, host: string, port: number, user: string,
            login_mode: "pem" | "password" (default "pem"),
            identity_file?: string, passphrase_env?: string,  # login_mode="pem"
            password_env?: string }                            # login_mode="password"
      # login_mode="pem"이면 identity_file 필수(passphrase_env는 암호화된 키만).
      # login_mode="password"면 password_env 필수. 둘 다 §9 원칙에 따라
      # 비밀번호/키 암호는 평문이 아니라 환경변수 "이름"으로 저장한다.
      # connection.uri(MongoDB 완전한 연결 문자열)나 connection.cluster_mode
      # (Redis Cluster)처럼 단일 host/port가 아닌 Connection은 Bastion 터널을
      # 자동 구성할 수 없다(server/connection/manager.py::_resolve_bastion_if_needed
      # 가 명확한 에러로 거부한다) — ssh.enabled를 false로 둔다.
  - ontology?: { enabled: boolean(default true), daily_build_time: string(default "02:00") }
  - connect_timeout_sec?: number(default 5)   # BaseAdapter.connect_timeout_sec가 읽음 (00 §33)
  - query_timeout_sec?: number(default 30)    # BaseAdapter.query_timeout_sec가 읽음 (00 §33)
  - secrets: Environment Variable 참조 (평문 저장 금지, 00 §9 원칙)
```

### 4.2 Ontology Document Schema

Vector Store에 저장되는 단위 문서(청크) — Container(Table/Collection/Index/Key 패턴) 단위로 구성하고 Field는 하위 필드로 포함한다. 필드명은 [00 §10.1](./00_개발요건사항.md)의 Namespace/Container/Field 일반화 용어를 사용한다.

```text
OntologyDocument
  - id: string                    # "{connection}:{namespace}:{container}"
  - connection: string
  - engine_family: "rdb" | "dw" | "document" | "search" | "keyvalue"
  - namespace: string             # Schema/Database/DB Number 등 (없는 Engine은 생략)
  - container: string             # Table/Collection/Index/Key Pattern
  - container_comment?: string    # 없는 Engine(MongoDB/ES/Redis)은 생략
  - row_count_estimate?: number
  - fields: {
      name: string
      type: string
      comment?: string
      is_pk: boolean              # Document/Search/KeyValue는 대부분 false
      is_fk: boolean
      fk_ref?: { container: string, field: string }
      inferred?: boolean          # Sampling으로 추론된 Field인 경우 true (MongoDB/Redis)
    }[]
  - embedding_text: string        # 임베딩에 사용된 원문 (예: "[prod-aurora].orders 테이블: 주문 정보. customer_id: ...")
  - source_hash: string           # 변경 감지용 (comment/필드 구성의 해시)
  - last_indexed_at: datetime
```

### 4.3 Table Relationship (ERD) Schema

`get_table_relationships` 출력 형식이자 ERD 렌더링 입력 형식이다. 3.5 참고.

```text
QALogEntry
  - log_id: string (uuid)
  - timestamp: datetime
  - connection: string
  - skill: string
  - question: string
  - tools_used: string[]
```

저장 위치: `data/qa_logs/<connection>/YYYY-MM-DD.jsonl` (일자별 append-only 파일. 향후 대용량화 시 경량 DB로 전환 검토, [11. 미결정 사항](#11-미결정-사항)).

## 5. Skill 라우팅 정의

Claude가 사용자 요청의 의도를 어떤 Skill로 연결하는지에 대한 기준이다. 순서는 우선순위이며, 상단 조건에 해당하면 하위 조건을 평가하지 않는다.

| 우선순위 | 사용자 의도 신호(예시 키워드/패턴) | Skill | 1차 호출 Tool |
|---|---|---|---|
| 1 | "ERD", "관계도", "다이어그램으로 그려줘" | `erd-builder`(공통 Skill, Maintenance/Tuner/DataEngineer 어디에도 속하지 않음) | `search_object_catalog` → `get_table_relationships` |
| 2 | "테이블/컬럼이 뭐야", "~관련 테이블 찾아줘", "무슨 의미야" | (공통 기반, Skill 아님) | `search_object_catalog` |
| 3 | 에러 메시지 포함, "장애", "에러 분석" | Maintenance / db-error | `db_error_analyze` |
| 4 | "느려", "slow query", "5초 이상" 등 특정 증상 언급 | Maintenance / slow-query | `slow_query_list` → `query_explain` |
| 5 | "인덱스 추천/개선", "쿼리 더 빠르게" (특정 장애 언급 없음) | Tuner / index-tuning, query-tuning | `get_table_statistics` → `index_recommend` 또는 `query_rewrite_suggest` |
| 6 | "원본 데이터", "파이프라인", "옮겨줘", "적재" | DataEngineer / data-pipeline | `list_raw_sources` → `generate_pipeline_plan` |
| 7 | "전에도 비슷한 질문", "자주 조회되는" | (공통 기반, Skill 아님) | `get_query_patterns` |
| 8 | 위 어느 것에도 명확히 속하지 않음 | Claude가 `search_object_catalog`로 대상을 먼저 확인 후 사용자에게 의도 재확인 | `search_object_catalog` |

모든 경로 종료 시 공통으로 `log_qa`가 호출된다([3.6](#36-learning-qa-logging--pattern)).

## 7. 주요 처리 흐름

### 7.1 Slow Query 분석 흐름

```text
사용자 질문
  → search_object_catalog (대상 테이블이 모호할 때만)
  → slow_query_list
  → query_explain (상위 N개 SQL)
  → Claude 분석 (Full Scan / Missing Index / Join / Sort 등)
  → 응답 + log_qa
```

### 7.2 Index 추천 흐름

```text
사용자 질문
  → get_table_statistics + get_index_statistics
  → query_explain (Before)
  → index_recommend
  → (선택) query_explain 재실행 또는 Cost 추정 (After)
  → Claude가 Before/After 비교 + Trade-off 설명
  → 응답 + log_qa
```

### 7.3 Pipeline 설계 흐름

```text
사용자 질문
  → search_object_catalog (Source/Target 후보 탐색)
  → list_raw_sources + get_schema (Source)
  → get_schema (Target)
  → profile_data (Source 품질 확인)
  → generate_pipeline_plan
  → validate_pipeline (Dry-run)
  → 응답 + log_qa
```

### 7.4 Object 검색(Ontology) 흐름

```text
사용자 질문 ("~관련 테이블 찾아줘")
  → search_object_catalog
  → 결과 score가 임계치 이상 1건이면 바로 사용
  → 여러 건이 근접하면 Claude가 사용자에게 재확인
  → 확정된 Object를 이후 Skill 실행에 전달
  → 응답 + log_qa
```

### 7.5 ERD 생성 흐름

```text
사용자 질문 ("ERD로 그려줘")
  → search_object_catalog (대상 Table이 이름으로 특정되지 않은 경우)
  → get_table_relationships (scope: 명시 목록 | related_to | schema)
  → Claude가 결과를 Mermaid erDiagram 문법으로 변환
  → 코드 블록으로 응답 (Claude Code가 자동 렌더링)
  → 응답 + log_qa
```

### 7.6 Q&A Logging & Daily 배치 흐름

```text
[요청 시점]
Skill 실행 완료 → log_qa (JSONL append)

[Daily 배치, Scheduled Job]
00:00~03:00 사이 순차 실행 (충돌 방지를 위해 아래 순서 고정):
  1. build_ontology_index (mode: incremental) — 전체 Connection 순회
  2. summarize_query_patterns — 전날 00:00~24:00 로그 대상
  3. 배치 실패 시 실패 사실만 로그에 남기고 익일 재시도
     (00 §41 비기능 요구사항: 배치 실패가 Skill 기능에 영향을 주지 않도록 격리)
```

## 8. 에러 코드 정의

[00 §32 Error Handling](./00_개발요건사항.md)의 에러 유형을 아래와 같이 코드화한다.

| 코드 | 대응 예외 클래스 | 발생 상황 |
|---|---|---|
| `CONNECTION_ERROR` | ConnectionError | DB 연결 실패, 타임아웃 |
| `SSH_CONNECTION_ERROR` | SSHConnectionError | Bastion 연결 실패 |
| `AUTH_ERROR` | AuthenticationError | 인증 실패 |
| `QUERY_ERROR` | DatabaseQueryError | SQL 실행 오류 |
| `QUERY_TIMEOUT` | QueryTimeoutError | Query Timeout 초과 |
| `DDL_BLOCKED` | ReadOnlyViolationError | Read Only 원칙 위반 SQL 감지 (INSERT/UPDATE/DDL 등) |
| `OBJECT_NOT_FOUND` | ObjectNotFoundError | 지정한 Table/Column이 존재하지 않음 |
| `AMBIGUOUS_OBJECT` | AmbiguousObjectError | `search_object_catalog` 결과 유사도가 근접한 후보가 다수 |
| `ONTOLOGY_INDEX_STALE` | (경고, 예외 아님) | Ontology Index 마지막 갱신이 설정된 배치 주기를 초과하여 결과 신뢰도가 낮을 수 있음을 안내 |
| `CAPABILITY_NOT_SUPPORTED` | (정상 응답, 예외 아님) | 대상 Engine의 Adapter가 Tool이 요구하는 Capability를 구현하지 않음([2.2](#22-database-adapter-인터페이스-capability-기반), [3.8](#38-tool--capability-매핑)) |

모든 에러는 Claude가 사람이 이해할 수 있는 문장으로 재구성해 응답하며, 원본 에러 코드/메시지는 [00 §31 Logging](./00_개발요건사항.md) 원칙에 따라 Password/Secret을 제외하고 로그에 남긴다.

## 10. 용어 정의 (Glossary)

| 용어 | 정의 |
|---|---|
| Skill | Claude Code Plugin이 제공하는, 특정 목적의 작업 절차를 담은 지침(SKILL.md) 단위 |
| MCP Tool | MCP Server가 노출하는 개별 기능 함수. Skill이 호출하는 실행 단위 |
| Ontology | Server-Schema-Table-Column의 comment 기반 계층적 메타데이터 구조 |
| RAG | Retrieval-Augmented Generation. 본 프로젝트에서는 Ontology를 Embedding하여 자연어 검색에 활용하는 방식을 지칭 |
| Cardinality (Index 문맥) | Index 컬럼 값의 고유성 정도 |
| Cardinality (ERD 문맥) | 두 Table 간 관계의 유형(1:1, 1:N 등) |
| Dry-run | 실제 쓰기(적재) 없이 변환/검증 로직만 Sample 데이터에 적용해보는 검증 방식 |
| Idempotency | 동일 Pipeline을 재실행해도 결과가 중복되지 않는 성질 |
| Confidence(declared/inferred) | ERD 관계가 DB에 실제 선언된 FK(declared)인지, 컬럼명 패턴으로 추정(inferred)한 것인지 구분하는 값 |
| Engine Family | RDB/DW/Document/Search/Key-Value처럼 저장소의 성격에 따른 분류. [00 §7.1](./00_개발요건사항.md) |
| Capability | 특정 Engine이 지원하는 기능 단위(SQL, SLOW_OP, SCHEMA 등). Adapter는 Capability 단위로 구현된다 |
| Adapter Registry | `db_type`과 Adapter 클래스를 매핑하여, 신규 Engine을 Skill/Tool 코드 변경 없이 추가할 수 있게 하는 등록소 |
| Namespace / Container / Field | Ontology의 일반화된 계층 용어. RDB의 Schema/Table/Column, MongoDB의 Database/Collection/Field, Redis의 DB Number/Key 패턴 등에 대응 |

## 11. 미결정 사항 (Open Issues)

00 문서에서 "검토 대상"으로 남겨둔 항목과, 본 문서 작성 중 발견된 추가 결정 필요 사항을 정리한다. 아래 항목은 Phase 착수 전 확정이 필요하다.

✅ 해결됨: Embedding Provider(sentence-transformers)·Vector Store(LanceDB) —
[00 §28](./00_개발요건사항.md), `server/catalog/embeddings.py`/`rag_index.py` 참고.

✅ 해결됨: Elasticsearch vs OpenSearch 클라이언트 분리 — 겸용 단일 클래스는
elasticsearch-py 8.x가 클러스터의 Elastic 제품 여부를 확인하는 product-check를
수행해 OpenSearch에 붙이면 거부/경고가 발생할 수 있어 위험 판단, **분리**로
결정. 공통 REST 호출 로직은 `server/database/search_base.py`(`SearchAdapterBase`)로
공유하고, Client 생성부만 `elasticsearch.py`(`ElasticsearchAdapter`)/
`opensearch.py`(`OpenSearchAdapter`)로 나눔. `AdapterRegistry`에 `elasticsearch`/
`opensearch` db_type이 각각 다른 클래스로 등록됨. `tests/test_multi_topology.py` 참고.

✅ 해결됨: Redis Cluster 모드 지원 — **지원**으로 결정. Connection Profile에
`connection.cluster_mode: true` + `connection.nodes`(시작 노드 목록)를 주면
`redis.cluster.RedisCluster`로 접속(`server/database/redis.py`). 기존 수동
SCAN cursor 루프는 노드마다 독립된 cursor 공간을 갖는 Cluster에서 틀린
결과를 내므로 폐기하고, 단일/클러스터 양쪽에서 동일하게 동작하는
`scan_iter()` 기반으로 교체. CLIENT LIST/SLOWLOG GET/INFO처럼 "리스트·dict를
반환하는 명령"은 Cluster에서 기본적으로 노드 하나만 조회되므로
`_all_nodes_list()`/`_all_nodes_dict_sum()`으로 전체 노드 결과를 병합.
`config/connections.example.yaml`의 `prod-cache-cluster` 예시, `tests/test_multi_topology.py` 참고.

✅ 해결됨: MongoDB Replica Set 연결 문자열 처리 — **지원**으로 결정.
Connection Profile에 `connection.uri`(완전한 연결 문자열, `mongodb+srv://` 포함)를
주면 그대로 `MongoClient`에 전달(`server/database/mongodb.py`) — pymongo가
seed list/DNS SRV 조회를 알아서 처리하므로 Adapter에서 별도 파싱 불필요.
`uri`가 없으면 기존 `uri_host`/`port` 단일 호스트 방식이 그대로 동작(하위 호환).
`_db()`는 `connection.database`가 없으면 `client.get_default_database()`로
URI에 포함된 기본 DB를 사용. `config/connections.example.yaml`의
`prod-mongo-replicaset` 예시, `tests/test_multi_topology.py` 참고.

✅ 해결됨: MSSQL Driver — 순정 Python 구현체 `pymssql`(FreeTDS 기반)로
확정, OS ODBC Driver 사전 설치 불필요(`server/database/mssql.py`).

✅ 해결됨: ClickHouse 분산 테이블(Distributed Engine) 처리 — **결정: 별도
대응 안 함**. 현재 실제로 Distributed 테이블을 운영하지 않아 지금 시점에
코드를 바꿀 이유가 없다고 판단(2026-09). Distributed 엔진 자체는 서버가
샤드 라우팅을 처리해주므로 단일 노드 접속(`clickhouse.py`)으로도 일반
쿼리는 그대로 동작한다 — 실제로 Distributed 테이블을 쓰게 되면 그때
`get_schema()`에 `engine` 컬럼 노출 여부를 재검토한다.

| 항목 | 관련 Phase | 비고 |
|---|---|---|
| Daily 배치 실행 방식 | 17, 19 | OS Cron vs MCP Server 내장 Scheduler. Plugin 설치 후 수동 설정을 최소화해야 하므로 내장 Scheduler를 우선 검토 |
| Tibero Slow Query 조회 View | 6 | Tibero의 Performance View 중 정확한 대상 확정 필요 (Oracle 호환 V$ 계열 추정) |
