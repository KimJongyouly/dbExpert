# dbExpert 개발 히스토리 — 배경에서 완료까지

이 문서는 dbExpert Plugin이 **왜 시작되었고, 어떤 순서로 만들어졌고, 중간에 무엇이
바뀌었고, 그 과정에서 무엇을 배웠는지**를 시간 순서로 정리한 기록이다.
[`00_개발요건사항.md`](./00_개발요건사항.md)(요건)와 [`01_개발정의서.md`](./01_개발정의서.md)(설계)가
"무엇을 만들기로 했는가"를 담는 SSOT라면, 이 문서는 "실제로 어떻게 진행되었는가"를 담는다.
설계 문서와 표현이 다르면 설계 문서가 기준이다.

전체 개발은 2026년 9월에 이루어졌다. 아래에서 "결정"이라고 적은 항목은 그 근거가
00/01 문서 또는 코드 주석에 남아 있는 것만 적었다.

---

## 1. 배경 — 왜 만들었나

### 1.1 문제

운영 중인 데이터 인프라는 하나의 DBMS로 끝나지 않는다. RDB(MySQL, PostgreSQL, Tibero,
MSSQL)에 DW(ClickHouse), Document(MongoDB), 검색(Elasticsearch/OpenSearch), 캐시(Redis)까지
서로 다른 Engine이 함께 있고, 대부분은 Bastion 뒤에 있다. 여기서 반복되는 일은 정해져 있다.

- "이 API가 느려졌다" → Slow Query 찍고, 실행계획 보고, Lock 걸린 세션 확인하고, 통계 정보 보고
- "이 테이블에 인덱스가 필요한가" → 카디널리티, 기존 인덱스 사용률, WHERE 절 패턴 확인
- "이 원본 데이터를 웨어하우스로 옮기려면" → 스키마 파악, 프로파일링, 매핑, 증분 적재 설계
- 그 전에 늘 "그 데이터가 어느 서버 어느 테이블에 있는지"부터 찾아야 한다

각 작업의 **절차는 DBA라면 누구나 알지만**, Engine마다 조회하는 시스템 뷰가 다르고,
Bastion 터널을 매번 열어야 하고, 결과를 해석해 설명하는 데 시간이 든다. 이미 Claude Code를
개발 도구로 쓰고 있었기에, "이 절차를 Claude가 대신 수행하되, DB를 절대 망가뜨리지 못하게"
만들 수 있다면 실질적인 시간이 절약된다고 판단했다.

### 1.2 핵심 아이디어

> **"DB에 대한 사실은 Python MCP Server가 수집하고, DBA/Data Engineer 수준의 판단과 설계는
> Claude가 수행한다."** ([00 §45](./00_개발요건사항.md))

Python 쪽은 Slow Query 목록, 실행계획, Lock 상태, 통계처럼 **사실(Fact)** 만 안정적으로 가져온다.
"이 인덱스를 추가해야 한다", "이 쿼리는 이렇게 고쳐야 한다"는 **판단**은 Claude가 하고, 실제
적용 여부는 사용자가 결정한다. 그래서 Python 코드에는 판단 로직을 넣지 않고, Skill(SKILL.md)에
"어떤 상황에서 어떤 Tool을 어떤 순서로 부르고 결과를 어떻게 해석할지"를 지침으로 적는다.

이 원칙은 나중에 몇 가지 결정을 자연스럽게 이끌었다.

- Read Only는 "권장"이 아니라 **구조적으로 강제**해야 한다 — Claude가 실수해도 DB가 바뀌면 안 된다.
- Engine이 늘어나도 Skill과 Tool 이름은 바뀌지 않아야 한다 — Engine 차이는 Adapter 계층에서만 흡수.
- Object 확인(어느 테이블/컬럼인가)은 Claude가 매번 추측하지 않고 **Ontology 검색**으로 사실에 근거한다.

## 2. 문서 먼저 — 요건정의서와 개발정의서

코드보다 문서를 먼저 썼다. 이유는 두 가지다.

1. Skill/Tool/Adapter/Ontology/학습 구조가 서로 얽혀 있어, 한 번에 전부 머릿속에 두고
   코딩하기엔 크다. Tool Input/Output, 데이터 모델, 처리 흐름을 먼저 고정해야 했다.
2. Claude Code와 함께 개발하는 방식이라, **문서가 곧 Claude에게 주는 명세**다. 문서가 정확하면
   구현 대화가 짧아진다.

| 문서 | 역할 | 주요 내용 |
|---|---|---|
| `00_개발요건사항.md` | What / Why | 목적, Skill 3분류(Maintenance/Tuner/DataEngineer), 8 Engine과 Capability 매트릭스, Connection/보안 정책, Ontology·학습 구조, 27개 Phase, MVP 완료 기준 |
| `01_개발정의서.md` | How | Adapter 인터페이스(Capability 기반), 23개 Tool의 Input/Output, Connection Profile·Ontology·Q&A 로그 스키마, 디렉터리 구조, 처리 흐름, 미결정 사항 |

그리고 규칙을 하나 정했다. **코드와 문서가 어긋나면 문서를 먼저 고치고 코드를 맞춘다.**
코드 주석 곳곳의 `Doc/00 §29`, `Doc/01 §3.9` 같은 참조는 이 규칙의 흔적이다. 실제로
구현 중 설계가 바뀐 항목(예: Elasticsearch/OpenSearch 분리, Redis Cluster 지원)은 모두
`01 §11 미결정 사항`에 "✅ 해결됨 + 결정 근거"로 남겼다.

## 3. 아키텍처 결정

```
Claude Code ── 자연어 ──▶ Claude ── Skill 선택 ──▶ MCP Tool (db-analyzer)
                                                      │
                                     ┌────────────────┼──────────────────┐
                              Connection Manager  Adapter Registry   Ontology / Q&A Store
                              (Direct·SSH Tunnel)  (db_type↔Adapter)  (LanceDB / JSONL)
                                                      │
                     MySQL · PostgreSQL · Tibero · MSSQL · ClickHouse · MongoDB · ES/OS · Redis
```

### 3.1 Claude Code Plugin + MCP Server

Plugin은 두 층으로 구성된다. **Skill**(SKILL.md 7개)은 Claude에게 주는 절차 지침이고,
**MCP Server**(`server/main.py`, FastMCP)는 Python으로 DB에 실제 접근하는 Tool 23개를 노출한다.
`.mcp.json`이 `uv run --directory ${CLAUDE_PLUGIN_ROOT} python server/main.py`로 Server를
띄우므로 Plugin 설치만으로 MCP Server가 함께 등록된다.

### 3.2 Capability 기반 Adapter + Registry

처음부터 8 Engine을 목표로 했기 때문에, RDB 3종을 만든 뒤 나머지를 붙이기 전에
**Adapter Registry & Capability 프레임워크**(Phase 22)를 먼저 도입했다. 각 Adapter는
`SQL`, `SLOW_OP`, `SCHEMA`, `RELATIONSHIP`, `COMMENT` 같은 Capability 중 지원하는 것만
구현하고, Tool은 `adapter.supports(Capability.X)`를 확인해 미지원이면 오류 대신
`CAPABILITY_NOT_SUPPORTED`를 돌려준다. Redis에 "FK 관계"를 묻거나 MongoDB에 "SQL 실행계획"을
물어도 Skill 코드는 그대로다.

### 3.3 Connection Profile: YAML + 환경변수 이름

접속 정보는 `config/connections.yaml`, 자격증명은 `.env`로 분리했다. YAML에는 비밀번호
대신 **환경변수 이름**(`password_env: DBEXPERT_PROD_AURORA_PASSWORD`)만 적고,
`ConnectionManager.load()`가 실행 시 `os.environ`에서 값을 읽는다. SSH Bastion은
`login_mode: pem | password` 두 방식을 지원하고, 터널이 열리면 Adapter가 보는 host를
`127.0.0.1:<local_port>`로 바꿔치기한다.

### 3.4 Ontology & RAG: 완전 로컬

테이블/컬럼 comment가 한국어와 영어가 섞여 있고, 메타데이터라도 외부 API로 보내고 싶지 않았다.
그래서 임베딩은 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`(384차원, 다국어,
CPU로 충분), Vector Store는 임베디드 LanceDB(파일 기반, 별도 서버 없음)로 결정했다.
Connection마다 `data/ontology_index/<connection>/lancedb/`에 독립 인덱스를 둔다.

### 3.5 Q&A 로깅과 쿼리 패턴 학습

Skill 실행 결과를 `log_qa`로 JSONL에 남기고, `summarize_query_patterns`가 주기적으로
Connection별 대표 쿼리 패턴(`patterns.json`)으로 요약한다. SQL 리터럴은 `?`로 마스킹해
저장한다. 이후 `find_query_pattern`이 새 질문을 같은 임베딩으로 벡터화해 과거 질문과
의미 유사도로 비교하므로, 비슷한 질문에는 재탐색 없이 과거 SQL을 조정해 답한다.

## 4. 개발 진행 — Phase별 기록

[00 §39](./00_개발요건사항.md)의 27개 Phase 로드맵을 따라 진행했다. 번호는 로드맵 순서이고,
실제 착수 순서는 아래 비고에 적었다.

### 4.1 기반 (Phase 1–4): "설치되고, 연결되고, Slow Query가 보인다"

| Phase | 내용 | Tool |
|---|---|---|
| 1 | Plugin 설치 → MCP Server 기동 → MySQL 연결 → 버전 조회 | `db_ping` |
| 2 | Slow Query 조회 (`performance_schema` 기반) | `slow_query_list` |
| 3 | 실행계획 조회. `EXPLAIN ANALYZE`는 기본 비활성 | `query_explain` |
| 4 | Direct / SSH Bastion(pem·password) 양쪽 지원 | — |

여기서 Read Only의 뼈대(`sql_guard.assert_readonly_sql`)와 Timeout(Connect 5초 / Query 30초,
Connection별 override)이 함께 들어갔다.

### 4.2 RDB 확장 (Phase 5–6, 22)

| Phase | 내용 | 비고 |
|---|---|---|
| 5 | PostgreSQL Adapter (`pg_stat_statements`, `pg_locks`) | |
| 22 | **Adapter Registry & Capability 프레임워크** | 로드맵상 22번이지만 Tibero 직후, Tuner 착수 전에 먼저 진행 |
| 6 | Tibero Adapter | 순정 Python 드라이버가 없어 **JPype로 JVM을 띄우고 JDBC를 직접 호출**. Oracle 호환 `V$` 뷰 사용 |

Tibero는 유일하게 DB-API cursor 모양이 아니어서 공통 `SqlAdapterBase`를 쓰지 못하고
`execute_readonly`를 직접 구현했다. 또 JDBC jar 파일명은 "tibero6"인데 실제 접속을 확인한
서버는 Tibero 5.0이라, 최초 연결 시 `RuntimeWarning`과 `ping()` 응답의 `driver_warning`으로
"검증된 조합이 이것뿐이다"를 알려주도록 했다.

### 4.3 Maintenance (Phase 7–9)

| Phase | 내용 | Tool |
|---|---|---|
| 7 | DB Error 분석 — 에러 메시지 + 그 시점 Session/Lock/Slow Query를 한 번에 수집 | `db_error_analyze` |
| 8 | Lock / Session 조회 | `get_locks`, `get_sessions` |
| 9 | 통합 장애 분석 — Skill 지침으로 Claude가 Error+Slow+Lock+Session+Plan을 종합 | (신규 Tool 없음) |

### 4.4 Tuner (Phase 10–12)

| Phase | 내용 | Tool |
|---|---|---|
| 10 | Table/Index 통계 조회 → Missing/Unused Index 탐지 → 추천 | `get_table_statistics`, `get_index_statistics`, `index_recommend` |
| 11 | 비효율 SQL 패턴 탐지 → 대안 SQL 제안 | `query_rewrite_suggest` |
| 12 | Before/After 실행계획 비교 | `query_explain` 재사용 |

DDL은 절대 실행하지 않고 제안만 반환한다. "적용 여부는 사용자가 결정"이 원칙이다.

### 4.5 DataEngineer (Phase 13–15)

| Phase | 내용 | Tool |
|---|---|---|
| 13 | Raw Data 소스 탐색, 스키마 조회, 프로파일링(Null 비율/Cardinality) | `list_raw_sources`, `get_schema`, `profile_data` |
| 14 | Source→Target 매핑, 변환 로직, Full/Incremental 적재 방식 제안 | `generate_pipeline_plan` |
| 15 | Dry-run/Sample 기반 검증, Target 제약조건 정합성 확인 | `validate_pipeline` |

샘플 조회는 최소 건수 + 마스킹 원칙을 따르고, 실제 적재는 하지 않는다.

### 4.6 Ontology / 학습 / ERD (Phase 16–20)

| Phase | 내용 | Tool |
|---|---|---|
| 16 | Schema/Table/Column comment 수집 → 임베딩 → LanceDB 색인, 자연어 검색 | `build_ontology_index`, `search_object_catalog` |
| 17 | Daily 증분 갱신 | 스케줄러 자체는 미구현 → **쿼리 트리거 기반 자동 갱신**으로 대체(아래 5.6) |
| 18 | Q&A Logging | `log_qa` |
| 19 | 쿼리 패턴 요약 / 조회 | `summarize_query_patterns`, `get_query_patterns` |
| 20 | PK/FK 관계 조회 → Mermaid `erDiagram` | `get_table_relationships` |

### 4.7 Engine 확장 (Phase 23–27)

| Phase | Engine | Family | 매핑 요점 |
|---|---|---|---|
| 23 | ClickHouse | DW | `system.query_log` / `system.processes`. FK 없음 → 관계는 항상 inferred |
| 24 | MongoDB | Document | 스키마는 샘플링 추론, Slow Op은 `system.profile`, Lock 유사 정보는 `currentOp` |
| 25 | Elasticsearch / OpenSearch | Search | `_search`/`_mapping`/`_stats`/`_cat`만 구현. 관계 Capability 없음 |
| 26 | Redis / ElastiCache | Key-Value | `INFO`/`SLOWLOG`/`SCAN`. Key 패턴 정규화로 Ontology 수집 |
| 27 | MSSQL | RDB | DMV(`sys.dm_exec_query_stats`, `sys.dm_tran_locks`), comment는 `sys.extended_properties`, 실행계획은 `SHOWPLAN_XML` |

### 4.8 로드맵에 없던 추가: Query Builder (01 §3.9, 00 §11.4)

Ontology와 쿼리 패턴이 쌓이자 "테이블명을 모르는 자연어 질문에 바로 답하기"가 자연스럽게
가능해졌다. 그래서 `find_query_pattern`(과거 유사 질문 검색)과 `execute_readonly_query`
(Claude가 구성한 임의 조회 SQL을 기존 3중 방어 그대로 실행)를 추가하고 `query-builder`
Skill을 만들었다. "학습된 패턴 우선, 없으면 Ontology로 새로 유추, 실행 후 반드시 `log_qa`"가
절차다. 이것으로 Ontology → 실행 → 로그 → 패턴 → 재사용의 학습 고리가 닫혔다.

## 5. 중간에 부딪힌 문제와 결정

구현 중 실제로 겪은 문제들이다. 대부분 `Doc/02_설치.md` §8과 코드 주석에 원인과 함께 남아 있다.

### 5.1 `mcp` 2.x가 서버를 아예 못 띄우게 했다

`uv sync`가 `mcp` 2.x를 받아오면서 `mcp.server.fastmcp` 모듈이 사라져
`ModuleNotFoundError`로 기동 자체가 실패했다(2.x는 `FastMCP`를 `MCPServer`로 개명). 재현 확인
후 `pyproject.toml`에 `mcp>=1.0.0,<2.0.0` 상한을 걸었다. 마이그레이션은 향후 과제.

### 5.2 MCP Server는 쉘 프로파일을 거치지 않는다

`~/.zshrc`에 `export`한 자격증명이 MCP Server 프로세스에 전달되지 않아, 서버가 기동 직후
자격증명을 하나도 못 찾고 죽었다. Claude Code 쪽에는 "CONNECTION_CLOSED"로만 보여 원인 파악에
시간이 걸렸다. Claude Code가 하위 프로세스를 로그인 쉘 없이 띄우기 때문이다. 해결은
`python-dotenv`로 Plugin 루트의 `.env`를 `server/main.py`가 **직접** 읽게 한 것. 어떤 방식으로
기동되든 같은 값을 본다.

### 5.3 Connection 하나의 실패가 서버 전체를 죽였다

초기 `ConnectionManager.load()`는 등록된 Connection 중 하나라도 환경변수가 비어 있으면
예외를 던져 서버 전체가 죽었다. Connection이 늘어나자 이건 견딜 수 없었다. 실패한
Connection만 건너뛰고 `list_load_errors()`로 사유를 조회할 수 있게 바꿨다
(`tests/test_connection_manager_resilience.py`).

### 5.4 Read Only를 "계정"에 의존하지 않기로 했다

원래 설계는 1) Read Only DB 계정, 2) SQL 텍스트 가드의 이중 방어였다. 그런데 운영 환경에서는
Engine마다 별도 Read Only 계정을 발급받기 어려운 경우가 흔하다. 계정에 기대지 않기로 하고
코드 레벨을 강화했다.

- 텍스트 가드에 `SELECT ... INTO OUTFILE/DUMPFILE`, MSSQL `SELECT ... INTO <table>`처럼
  "SELECT로 시작하지만 쓰기 부작용이 있는 구문" 차단 추가.
- **3번째 방어선**: 연결 직후 서버 자신이 세션을 Read Only로 강제.
  MySQL `SET SESSION TRANSACTION READ ONLY`, PostgreSQL `default_transaction_read_only=on`,
  ClickHouse `settings={"readonly": 1}`, Tibero `Connection.setReadOnly(true)`.
- 통합 테스트 `test_server_itself_rejects_writes_even_if_sql_guard_is_bypassed`가 실제
  MySQL/PostgreSQL 컨테이너에서 "Python 가드를 완전히 우회해 raw connection으로 DELETE해도
  서버가 거부"함을 증명한다.
- MSSQL은 T-SQL에 세션 전체 Read Only 강제 수단이 없어 3번째 방어선을 둘 수 없다. 문서에
  "MSSQL만큼은 별도 Read Only 계정을 강력히 권장"으로 명시했다.

### 5.5 Elasticsearch와 OpenSearch를 한 클래스로 못 묶었다

`elasticsearch-py` 8.x는 접속 시 서버가 진짜 Elastic 제품인지 product-check를 하기 때문에
OpenSearch에 붙이면 거부/경고가 난다. 공통 REST 로직은 `search_base.py`로 공유하고, Client
생성부만 `ElasticsearchAdapter` / `OpenSearchAdapter`로 분리해 Registry에 각각 등록했다.

### 5.6 Daily 스케줄러 대신 "쿼리 트리거 자동 갱신"

Phase 17의 Daily 배치는 "OS Cron vs 내장 스케줄러"가 미결정이었고, "설치 후 수동 설정 최소화"
원칙과도 충돌했다. 대신 **Claude가 어떤 Table에 쿼리를 실행하는 순간 그 Table의 Ontology를
백그라운드에서 갱신**하는 방식(`catalog/auto_refresh.py`)을 넣었다. 같은 날 이미 갱신한
Table은 건너뛰고, `query_scope.extract_table_names()`가 SQL의 FROM/JOIN에서 Table을 뽑아
JOIN 대상 전부를 포함한다. 실패해도 원래 Tool 응답에는 영향이 없다(best-effort). 인덱스가
비어 있는 Connection에서 `search_object_catalog`를 부르면 그 자리에서 전체 스캔으로 한 번 채운다.

### 5.7 Q&A 로그는 "컴퓨터가 한가할 때" 쓴다

`log_qa`가 Tool 응답을 지연시키지 않도록 `QALogWriter`가 큐에 쌓아두고, `psutil`로 CPU
여유를 확인하고 최근 Tool 호출이 없을 때(`activity.touch()` 기준)만 디스크에 쓴다.

### 5.8 Redis Cluster에서 SCAN cursor가 틀렸다

수동 `SCAN` cursor 루프는 노드마다 독립된 cursor 공간을 갖는 Cluster에서 틀린 결과를 냈다.
`scan_iter()`로 교체하고, `CLIENT LIST`/`SLOWLOG`/`INFO`처럼 노드 하나만 응답하는 명령은
전체 노드 결과를 병합하도록 했다. `cluster_mode: true` + `nodes` 설정으로 지원.

### 5.9 MSSQL 드라이버: pyodbc 대신 pymssql

`pyodbc`는 OS에 ODBC Driver 사전 설치가 필요해 "설치 후 수동 설정 최소화" 원칙과 충돌했다.
FreeTDS 기반 순정 Python 구현체 `pymssql`로 결정.

### 5.10 FK가 선언되지 않은 스키마에서 ERD 그리기

실제 스키마 상당수는 FK 제약이 전혀 없다. `get_table_relationships`는 컬럼명 접미사
(`_id/_cd/_code/_no`)로 관계를 추정(inferred)하는데, `_idx` 접미사를 쓰는 관행에서는 자동
추정이 걸리지 않았다. 대신 컬럼 comment에 "참조 테이블.컬럼"이 적혀 있는 경우가 많아,
`erd-builder` Skill은 Ontology comment를 추정 근거로 함께 쓰고 `confidence: inferred`인
관계에는 반드시 `(추정)`을 표기하도록 했다. 관계 추론 시 단어 1개만 겹치는 comment(예: "총 세대수" vs
"세대수")는 오탐이 많아 제외한다.

### 5.11 Marketplace 등록에는 별도 매니페스트가 필요했다

`claude plugin marketplace add <폴더>`는 단일 Plugin 폴더로는 안 되고
`.claude-plugin/marketplace.json`이 있어야 했다(`Marketplace file not found`). 처음엔
`--plugin-dir` 플래그로만 쓰다가, 배포를 위해 저장소 자체를 단일 Plugin 마켓플레이스로 만드는
`marketplace.json`을 추가했다. 그래서 설치 명령이 `dbExpert@dbExpert`다.

### 5.12 HuggingFace 모델은 "설치"가 아니라 "첫 호출"에 받아진다

`uv sync`는 `sentence-transformers` 라이브러리만 설치하고, 모델 가중치(약 460MB)는 Ontology
Tool을 처음 호출하는 순간 Hub에서 받아온다. 처음엔 이걸 몰라 첫 `search_object_catalog`가
왜 이렇게 오래 걸리는지 의아했다. 설치 문서에 "언제·무엇을·얼마나 받는지"를 별도 장으로
쓰고, 미리 받아두는 스크립트(`scripts/download_embedding_model.py`)와 폐쇄망용 로컬 경로
지정(`DBEXPERT_EMBEDDING_MODEL`)을 추가했다.

작동하는지 확인한 사례였다.

## 8. 배운 것

1. **문서를 SSOT로 두는 것이 Claude와 함께 개발할 때 가장 큰 레버리지였다.** 명세가 문서에
   있으면 구현 대화는 "01 §3.5대로 만들어줘"로 끝난다. 설계 변경도 문서의 "미결정 사항"
   절에 결정 근거와 함께 남기니 나중에 "왜 이렇게 했지"가 사라지지 않았다.
2. **"판단은 Claude, 사실은 Python"을 지키면 코드가 작고 안정적으로 유지된다.** 인덱스 추천
   휴리스틱을 Python에 넣고 싶은 유혹이 여러 번 있었지만, Skill 지침으로 옮기는 쪽이 항상
   더 나았다.
3. **Read Only는 텍스트 검사로 끝나지 않는다.** 함수/프로시저 안의 쓰기 부작용은 텍스트로
   못 잡는다. 서버가 스스로 거부하게 만드는 층이 있어야 하고, 그것을 실제 DB로 증명하는
   테스트가 있어야 안심할 수 있었다.
4. **Capability 프레임워크를 Engine 확장 전에 넣은 것이 옳았다.** 이후 5개 Engine을 추가하며
   Skill/Tool 코드를 한 줄도 바꾸지 않았다.
5. **MCP Server의 실행 환경은 사용자의 쉘이 아니다.** 환경변수, 캐시 경로, 모델 다운로드처럼
   "내 터미널에서는 되는데" 류의 문제가 여기서 나온다. `.env` 직접 로드로 일관되게 해결했다.
6. **"첫 호출에 받아지는 것"은 반드시 문서에 써야 한다.** 460MB 모델 다운로드를 사용자가
   모르고 있으면 도구가 고장 난 것처럼 보인다.
